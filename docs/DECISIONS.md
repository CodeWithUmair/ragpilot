# Decision log

Newest last. Each entry: the decision, why, and what was rejected. Add an entry
whenever you make a choice a future reader might question.

### D1 — Rebuild the backend in FastAPI, keep the Next.js frontend (2026-09-27)
**Why:** The goal is to prove Python AI-backend skills (FastAPI, async, Pydantic,
LangGraph) on a real product. The AI layer is Python-native; the frontend was
already good. **Rejected:** a full rewrite (no extra signal), NestJS (already the
owner's strength — no new proof).

### D2 — Keep the exact API contract of the Express backend
**Why:** The frontend then works unchanged, which makes the port verifiable (same
UI, new engine) and keeps scope honest. **Cost:** some wire names are camelCase and
a few quirks survive (e.g. `GET /api/chat`). See `API_CONTRACT.md`.

### D3 — Re-implement the Better Auth protocol instead of a new auth scheme
**Why:** The frontend uses `better-auth/react`; a byte-compatible Python version
(scrypt hash format, HMAC-signed tokens, `set-auth-token`) means no frontend auth
rewrite AND existing users of the legacy DB can still log in. **Rejected:**
fastapi-users/JWT (would force frontend changes and password resets).

### D4 — Bearer tokens, not cookies
**Why:** Dashboard and API are on different sites (Vercel vs DigitalOcean);
third-party cookies are blocked by Safari/Brave. Google OAuth uses a top-level
navigation so its state cookie is first-party, then hands the token over in the URL
fragment (never sent to servers or logs).

### D5 — Same database schema as Prisma (quoted camelCase), SQLAlchemy maps to snake_case
**Why:** The new backend can point at the existing production DB with zero data
migration. Pydantic aliases convert back to camelCase on the wire.

### D6 — One idempotent raw-SQL initial migration
**Why:** It must be safe on both an empty DB and the legacy Prisma DB (create only
what's missing, never drop). Autogenerated Alembic ops can't express pgvector's HNSW
index and aren't idempotent. It also restores the HNSW index Prisma dropped by accident.

### D7 — LangGraph for the chat flow — but only where it earns its place
**Why:** The failures seen in real conversations needed branching and a loop:
follow-up questions retrieved nothing (needs "rewrite, then retrieve again",
bounded), greetings wasted retrieval (needs routing), lead-capture timing was
tangled conditionals (needs isolated, testable decisions). A graph expresses these
as explicit nodes/edges tested with fakes. **Rejected:** LangChain chains/agents
(abstraction without benefit here), a multi-agent design (overkill), wrapping the old
linear function in a single-node graph (buzzword only).
**Not using LangChain components** (loaders, splitters, retrievers): the hand-written
ingestion/retrieval encodes project-specific fixes (boilerplate filtering,
content-hash dedupe, relative gating) that generic components don't.

### D8 — Deterministic heuristics (regex) for contact extraction, lead intent and small-talk routing
**Why:** They run on every message; an extra LLM call would add latency and cost.
They are conservative by design (a wrong auto-captured name is worse than none).
Upgrade path: an LLM classifier node in the graph if precision ever demands it.

### D9 — Query rewrite only on weak retrieval of a follow-up, max once
**Why:** Rewriting every message would add an LLM round-trip to every turn.
`CONFIDENT_SCORE = 0.35` (raw cosine of the best match) decides; first messages
never rewrite (nothing to resolve). `MAX_REWRITES = 1` bounds cost/latency.

### D10 — Provider-agnostic models behind Protocols; any OpenAI-compatible endpoint
**Why:** Tests use fakes; switching to Groq/Together/local vLLM is `OPENAI_BASE_URL`
+ model names. Embeddings must stay 1024-dim to match the column.

### D11 — `VectorStore` protocol with pgvector as the first implementation
**Why:** The owner plans vector-DB changes. Keeping Postgres first means tenant
isolation, transactions and joins stay simple; swapping is one class.

### D12 — Streaming via SSE (not WebSockets)
**Why:** One-way token stream, works through nginx/CDNs with buffering disabled,
and the frontend already consumed SSE with `fetch` + a stream reader (needed because
`EventSource` can't send the bearer header).

### D13 — Training runs inside the request (SSE) with a 5-worker pool
**Why:** Simple, gives live progress, fine for ≤ 50 pages. Client disconnect cancels
the pool so no money is spent on abandoned runs. **Revisit** with a job queue when
sites get bigger (see ROADMAP).

### D14 — SSRF guard on all server-side fetches of user-supplied URLs
**Why:** On a public server, "train on http://169.254.169.254/" or "localhost:5432"
would leak internal data through the chatbot. Checked per request including
redirects; off outside production for local testing.

### D15 — Deployment: Vercel (frontend) + DigitalOcean App Platform (API) + Neon (DB), custom domain later
**Why:** No DNS yet; App Platform gives HTTPS on `*.ondigitalocean.app` (a Vercel
HTTPS page can't call a plain-HTTP IP). The API runs on the owner's client's
DigitalOcean account. The single-VPS compose + nginx setup (`deploy/`) remains ready
for when `rag.umairamir.com` is configured. Neon: free, serverless Postgres with
pgvector; use the direct (non-pooled) URL because asyncpg's prepared statements
break behind PgBouncer transaction pooling.
